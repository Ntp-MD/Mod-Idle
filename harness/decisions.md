| D-113 | applied · owner ruling | **The data owns every number and the doc is its projection — one direction, enforced.**
The owner asked how to make the game and the docs a single source of truth now that there is a playable page, and ruled for the proposal. The measurement that framed it: **5,981 numeric tokens sit inside the 68 generated blocks, and 4,232 sit in prose across 42 docs that no writer owns.** A prose number cannot move when the data moves and nothing detects it going stale — which is exactly how `Dodge flat 3-15` survived into files after the line was retired, and how the published ceiling stayed at 816 after `Core Stat %` was removed.
**Two changes, in the order that makes the second enforceable.** First, the direction: `X15` used to parse the "Total" column back out of `mod-pool.md` and compare it against the engine, which made the **doc** a second source of a number the engine already had — the two could disagree and the doc would win. It now reads `mods.json`, the file that owns the ranges, and only reports. The read-back rule for the retired `K_dodge` went with the key. Second, the ban: **a number may only appear inside a `BEGIN GENERATED` marker**; prose names the key (`Int x K_INT_ES`) and never the value. Gate **L9** counts the lines that break it and fails when the count rises above `engine.json` `doc_prose_lines_max`.
The cap lands at the **measured** 1,390, not at zero, because 1,390 prose lines break the rule today and a gate that fails on day one blocks every other pass without telling anyone anything new. It is a debt to lower, never a target to hit: **every pass that fixes lines lowers the cap in the same edit**, because a rule whose own text moves the count is not a rule. That mechanic proved itself within the hour — `AGENT.md` was edited to state the rule, which raised the count by 2 and L9 failed, and restoring `skill-pool.md` from git after a writer emptied it raised it by 20 more. Both were caught by the gate rather than by reading.
Exempt: `harness/decisions.md` · `todo.md` · `handoff.md` · `HARNESS.md` (history and agent ops, which quote numbers as they were) and any line marked `lint:allow`.
**Still open and not fixed by this:** `combat.md` lost ~140 lines of uncommitted prose when `tools/survival.js --write` overwrote the whole file, and `skill-pool.md` the same way; both were restored from git, which returns the committed version and not the owner’s working copy. A writer that can empty a doc is a second defect independent of this ruling — it should refuse to write when the marker pair is missing rather than truncate the file. |

| D-109 | applied | **A pool now spends only what stands in it, so nothing reads below nothing.** The report was that the Mana and Energy Shield bars could go negative — and a negative pool is not a rounding to hide, it is state that has spent the same resource twice. The cause was the incoming split: `mobSwing` measured the shield against `c.es`, the sheet’s *maximum*, while the caller subtracted from the pool actually left, so a swing landing on a half-recharged shield took more than was there and drove the stored number under zero — and HP quietly absorbed less than it should have, because the hit had already been “paid for” twice. `mobSwing` now receives the live pool (an optional parameter defaulting to the sheet value, so every existing caller reads the same way) and clamps the split to it, which moves damage *between* the two pools instead of deleting any of it. `tick` also bounds both pools at the top of every second — never below nothing, never above what the sheet says they hold — because that is the state the bars print straight. Proof is two-sided: `game/tests/poolFloors.test.ts` shows one swing cannot spend more shield than stands and that the swing totals the same either way, then runs 3,000 seconds of hunting and reports the lowest shield and lowest mana it saw (0 and 48) with no negative and no over-full reading, and refuses to pass if the run never actually spent a pool. The running page was then stepped for 1,400 seconds and printed no minus anywhere — its lowest Energy Shield reading was exactly 0, which is the case that used to go under. ## D-026 — Energy Shield: what stat, how big, and why player-only (applied)

D-019 left one defence layer with no anchor, and one open fork about which stat owns it (`core-stats.md` says Int · the D1 note recommended Str).

**Stat — Int, and Str was rejected on the numbers.** Str 12 is already the top DPS row (9,847) and owns power + weight + armour; adding a fourth line to it widens the 2.6x build gap that is still an open fork (`formula.md` section 0). Int already owns four lines but they are one theme — the cast resource — and an Int build is the glassiest thing in the sheet, so the shield is the answer that build actually needs. `core-stats.md` keeps its published wording.

**Size — `K_INT_ES` 4**: Int 816 = **3,264**, which is exactly **40.0%** of the same build's 8,160 HP (Vit 210 at level 100). **X25** holds that share between 30% and 45% — high enough that a caster trades raw HP for something that comes back, low enough that it is never two health bars.

**Recharge — `K_INT_ESREGEN` 0.10 with the 5 sec delay already published in three files**: 81.6/sec, so the whole pool returns in **40.0 sec** of not being hit. That is not a taste number: 40 sec is the span the mana pool was retuned to (B5), and it is about 2.4x faster than a Vit build recovers its HP — a shield is meant to be the quick layer. The delay is the cost: 5 sec is long against a 1-sec trash clock, so ES refills *between* groups and not during a boss, which is what keeps the boss gate a pool-times-time question (combat.md section 7) rather than a heal loop. The `es_delay 3 sec` sketched in the D1 note is superseded — three files already said 5, and 5 is what makes the layer rhythmic.

**Player-only.** Mobs have an Int line but no shield: their survivability is anchored on `mob_HP`, so a second mob pool would count the same anchor twice (checks.md H1). **X25** fails if an ES value ever appears on a roster row.

**What this opens**: the boss survivability tables (combat.md §6/§7) now have a fourth input — an Int build takes 40% more effective damage before HP — which is one more reason those hand-carved tables need the `tools/survival.js` rebuild, and it does not change any published kill-rate or timeline number because ES is defensive, not a speed stat.

## D-024 — A mob dodges the way we do (applied)

## D-022 — Armour is one Str line on both sides (applied)

`K_ARMOUR` = **2**, reduction `armour ÷ (armour + 5 × raw physical)`, no Cap — the diminishing curve is the limit, exactly as `core-stats.md` already described it.

**Why the old anchor was wrong**: 731 was solved from `armour ÷ (armour + 5 × 1316) = 10%`, treating a boss's whole hit as physical. The incoming split is 50% physical + 50% Element (combat.md · D2), so the divisor saw twice the damage that actually reaches armour. Restated against the physical half, that same target is trivially reachable — so the anchor had to be re-derived rather than adjusted.

**Measured at the zone-9 edge (all printed by X22)**: a full-Str player is `816 × 2` = 1,632 armour, which cuts the boss's physical half by **35.0%** and a trash mob's by **68.2%**. Pointed the other way, the heaviest mob armour in the game — a Golem at level 80 — costs a max physical hit **2.3%**.

**Why that asymmetry is the point**: the ratio divides by the *raw hit*, so armour is strong against many small hits and weak against one big one. That makes armour the answer to trash groups and to fast low-damage weapons, and no answer at all to a boss — which is already this game's rule that bosses are gate-checked by pool × time, not by mitigation (encounter model). Magic and the 5 Elements ignore armour entirely, and chill's 25% Armour cut (D-018) now has real targets on the Golem · Knight · Orc rows.

**Guard**: **X22** fails if the boss cut leaves the 25-40% band, if armour stops answering trash mobs, or if any mob's armour can cost a max physical hit more than 10% — the last clause is what keeps armour from becoming a wall against the player.

## D-021 — Mob evasion is a Dex line, not a level number (applied)

D-019 gave every species a full stat block, but evasion stayed `mob_level × 1` — a stand-in written before mobs had a Dex at all. Two things were wrong with it: a Slime (Dex ×0.73) and an Elf (Dex ×1.25) were equally hard to hit at the same level, and the body classes already carried an `evasion` multiplier (Small ×1.10 · Large and Elite ×0.90) that no formula ever read. The column was dead data.

**Ruling — one K, both directions.** `K_EVASION` = **0.5**:

```
mob evasion    = stat_c(mob level) × species.dex × 0.5 × body class
player evasion = Dex × 0.5 + Gear Evasion flat (range still TBD)
hit_chance     = accuracy / (accuracy + evasion)      same roll either way round
```

**Why 0.5 and not a fitted number** — two independent reasons point at the same value:

- **The anchor does not move.** `stat_c × 0.5` at the roster's mean Dex multiplier (0.962) is 101 evasion at level 100, against the retired curve's 100. Reference mob is therefore defined as *the mean species vector on a Medium body*, not as an imaginary ×1.00 lineage. Published hit chances hold exactly as written — 80% with no Dex, 93.8% at the accuracy ceiling — so the DPS anchor, `mob_HP`, and the E1-E5 hour checkpoints needed no re-tune. A rebalance dressed as a derivation would have failed **X21**.
- **The offence: defence ratio is legible.** `K_DEX_ACC` 1.5 against `K_EVASION` 0.5 is 3:1, so two sides with equal Dex leave the attacker landing 75%. The defensive line is deliberately the weaker one per point, which is what keeps a single stat from approaching untouchable while still being worth items.

**What it changed in play (all generated, `formula-utility.md` section 8)** — the species spread runs 77 to 131 evasion, so a 0-item player hits between 75.0% and 83.7% depending on *what* is being hit, and Full Dex buys 92.1-95.2%. Pointed the other way, the top accuracy tier (Wolf · Elf · Drake) lands 43.6% on a Full-Dex player before Dodge even rolls, and the ×0.05 tier lands 3.7%.

### Consequences still open

- **Gear Evasion flat is still TBD.** The stat line now answers "how evasive is this Dex build", but the *item* half of the layer has no range, so a Dex build cannot yet buy the layer with slots. This is D1 step 4, and it is the reason `mod-pool.md` keeps the row as TBD.
- **Mob dodge has no contest rule.** The mob sheet's `dodge` column divides the mob's Agi rate by *the mob's own accuracy*, which is self-referential; it should be opposed by the attacker's accuracy. Two roster files (`skill-pool-curse.md` · `skill-pool-system.md`) still say monsters have no dodge, which the column already contradicts. Needs one ruling, not two.
 — **resolved in D-024.**
- **`combat.md` §2 step 1 was stale** — it still read "perfect_dodge (Cap 5%)" while D-012 removed that Cap in favour of the 30% ratio ceiling. Corrected in the same pass, since the step list is the order the new evasion roll lives in.
- **Evasion now sits ahead of Dodge on the player side too**, so the D6-D14 survivability tables will shift when `tools/survival.js` is finally built: those builds carry Dex 210-328, which is a real miss chance against a species accuracy tier, not the flat 0 the old model assumed.

## D-019 — Mob species and body classes (applied)

A mob is three independent axes. **Species** is a creature lineage, **body class** is one of Ragnarok's four card sizes, and **innate Element** stays a roll on spawn (already decided in `world.md`). The player has no class, so nothing here is a job.

**14 species**, spread across the 9 zones: Rat · Husk · Goblin · Slime · Bandit · Spider · Wolf · Orc · Troll · Elf · Demon · Knight · Drake · Seraph.

- **A species is a multiply vector on the player's own stat block.** Every mob starts at `stat_c` per stat, then the species multiplies it — so total mob power stays put and `mob_HP` keeps deriving from player DPS. Check **X19** fails any species whose seven multipliers do not average 1.00; every vector was normalised to hit that.
- **The accuracy tier is the load-bearing column, and it is what finally makes the dodge Cap answerable.** Mob accuracy is the shared `stat_c × K_DEX_ACC` scaled per species: against ×0.25 species (Husk · Slime · Knight) full Agi reaches the **90 Cap**; against ×1.00 species (Wolf · Elf · Drake) the same build only reaches the low thirties. This is why `checks.md` C1 could never be closed with one mob accuracy number — the species mix closes it, and dodge becomes a build that works *against some things* instead of a stat that is either capped or useless.
- **Four card sizes, copied from Ragnarok**: Small ×0.7/×0.7 · Medium ×1.0/×1.0 · Large ×1.7/×1.35 · Boss ×15/×4. **Elite is a rarity flag, not a fifth size** — an Elite is always a Large body carrying its own ×6/×4, so no two multipliers ever stack.
- Size raises HP faster than PS: a Large body is a longer fight, not a harder hit. That is what makes Small the farming body and Large the roadblock.
- `element_bias` only tilts the roll inside the zone's own 1-2 Elements. It never introduces one, so res still has to be prepared in advance.
- A species is not zone-locked: the same species in two zones is the same species at a higher level, never a reskinned one.
- **Both tables are generated** (`world.md` `mob-sheet`) from `engine.json` `mob`, so a stat vector or an accuracy tier is edited in the data, not in prose.

### Consequences still open

- **Mob crit now exists.** Lck flows into crit through the same K values a player uses, so the incoming damage order in `combat.md` §2 needs a crit step it never had. Not yet added.
- **Mob elemental resistance** now derives from mob Vit. `world.md` never stated a value, which means the player can currently reach res 75 with nothing to spend it on. Needs a ruling.
- With mob Str feeding armour through the same rule the player uses, **chill's 25% Armour cut acquires a real target** without waiting for the rest of D1 — but only once mob armour is actually stated.

## D-018 — The Elements dismantle defences (applied)

The five statuses stopped being "damage that happens over time" and became the layer that **takes the player's defences apart**, while physical/bleed brute-forces the same target. Three additions, all from the owner:

| status | new effect | value |
|---|---|---|
| burn | cuts the target's **HP regen**, 10% of it per stack | 5 stacks = **−50%** (regen 10 → 5) · no separate Cap, the stack count is the Cap |
| chill | cuts the target's **Armour** | **25%** (`armour_mult = 0.75`) |
| shock | cuts the target's **attack speed**, and cuts **our own Alignment against that target** | **−20% aspd** (own Cap 20) · **our Alignment × 0.80** |

Burn also moved from **3 stacks / 4 sec to 5 stacks / 5 sec**, for a reason the numbers gave away: 5 × 0.30 = **1.50**, exactly the global DoT Cap. A maxed fire build now fills the whole DoT budget by itself and poison contributes nothing until burn drops a stack, which turns that Cap from a safety net that never binds into a wall a build actually runs into.

- **burn regen cut** is the strongest of the three because `hp_regen` is not a side stat: Push downtime is `Max HP ÷ (hp_regen × 8)` and field rule 2 has tanks surviving bosses *because* regen keeps working during the fight. It is also the sustained version of what shock already did for one second. Counter: res, perfect dodge, and healing skills — no stat reduces it.
- **chill Armour cut is inert today.** Mobs have no Armour stat (`checks.md` D18 gates any skill referencing mob armour), so the rule has no numbers behind it until D1 gives mobs Armour. Written now so it is correct the moment that lands, and flagged there to be re-verified in the same pass.
- **shock is now a sacrifice, not a debuff.** It is the only status that fights our own: the more shock we land, the harder every other status is to apply to that target. Time control and sustained status compete for the same target instead of stacking. The Alignment cut is applied to the *target's* tolerance, not to our stat.
- Attack-speed reduction does not sum today — chill and shock each carry their own Cap 20, and `Rimbo Form` adds on top of chill. Left unsummed on purpose, with the worst case named in `elements.md` for the balance audit: if it is too strong the fix is one shared attack-speed Cap, not smaller numbers.
- **Mob side is pending.** `combat.md` §5 now carries all three against the player with full values, and `engine.json` `status.mob_side` records that the mirror ruling (halved like chill and shock, or full) must be made together with the owner's mob skill lists — a mob that cuts our Alignment attacks the stat every other status depends on.

## D-017 — Crit is physical only (applied)

Magic damage does not crit, and neither do the 5 Elements. `Critical damage %` is therefore a **single** line, 12-120%, and the former `Critical damage % (magic)` row is deleted from `mod-pool.md`.

- Reason: crit is the physical build's payoff. If magic crited on the same terms, the physical/magic weapon choice in `equipment-weapon.md` would go cosmetic — every weapon would want the same crit gear, and the 12-types-equal-DPS rule (D10) would hide a real build difference instead of expressing one.
- `magic` weapons may still roll `Critical damage %`; it simply does nothing for them, which is the honest signal that a caster is not a crit build.
- `combat.md` §2 step 2, `skill-pool-system.md` rule 8, `elements.md`, `core-stats.md`, `character-sheet.md` and `equipment-slot*.md` all updated. `formula-offense.md` now carries one formula, `crit_dmg = 100 + crit_dmg_pct + crit_overflow`.

## D-016 — Alignment resolved, Wis resolved, F9/F10 derived (applied)

**Alignment pays twice.** The doc said two opposite things: line 34/40 claimed Alignment "gates only status application", while the burn and poison formulas were computed from `elem_aligned_damage`. The measured table settled it — burn 3 stacks at 524/sec is only reachable from aligned damage (2,207 × 0.264 × 0.30 × 3), not from raw Element damage. So the ruling is:

- The **direct hit** lands in full and is never scaled by Alignment (P0-1 unchanged).
- The **status it inflicts** is scaled by Alignment, and Alignment is also the gate that lets the status land at all.
- Reason: a status that is only gated would stop caring how much Element damage the build has, which would make the Element stat itself irrelevant once the gate is passed.
- **Mark is the deliberate exception.** Every other Element's status converts the hit into a number (`elem_aligned_damage × K`); mark multiplies the hit instead, so Alignment enters it exactly once, as the gate. Letting Alignment scale mark as well would make the biggest stack payoff the one least about commitment to a target.

**Wis keeps a single benefit.** The stat sheet is "power + one utility" per stat, and Wis breaks it. Ruling: cooldown reduction is a *pacing* stat — it changes how often the list is pressed, never what a press is worth — so it needs no second benefit, and every candidate for one (effect duration, a mana reserve) is a larger system than the gap it would fill. Recorded rather than left as an open hole.

**F9 / F10 derived, T10b closed.**

| Row | Value | How |
|---|---|---|
| F9 Add mod stone/hr | **6.25** | elites carry a 25% chance (0.5% of 1,800 kills = 9 elites → 2.25) + bosses drop 1 each (4/hr) |
| F10 Ascend/hr | **3.75** | Ascend costs 1 Add + 8 tier stones, so `min(F9 ÷ 1, F7 ÷ 8)` — the scarcer stone sets the pace |

The result is that **tier stones bind**, not Add stones: a full 12-piece Ascend needs 16 hr of tier stones against 1.9 hr of Add stones, so Add stones pace the set piece by piece while the set itself waits on Refine. That is the intended shape from `crafting.md` — Ascend is the slowest craft and needs planning.

T10b now proves the Armourer floor against F9 as well: repair at 14 m (12 m at Ironrow) must exceed **9.60 m** of hunting per Add stone, and it does. The floor got *higher* when F9 landed, because Add stones are rarer than tier stones — so the repair line can never become a bad deal after the Add rate is known.

## D-015 — Bleeding, copied from Path of Exile (applied)

Bleed is **physical damage over time**. Rules taken from PoE:

- **Not an Element.** No Element tag, no Elemental resistance, no counter-pair row, no Mod line. It is not a sixth Element — Elements are the third *damage* path, bleed is a status on physical.
- **Does not stack.** One bleed per target; a new application refreshes the duration and replaces the stored damage when the new hit was stronger. No stack count exists anywhere.
- `bleed_total = physical_hit × 0.70`, `bleed_dps = bleed_total / 5 sec` — **does not scale with attack speed**, so slow heavy hits are the bleed build and the poison build is its opposite.
- **Cannot crit** (uses the non-crit physical part) and **armour does not reduce it**, matching the rule already written for all DoT in `combat.md` §2. Armour helps indirectly by lowering the inflicting hit.
- **Not a hit**, so dodge / perfect dodge / accuracy never touch it.
- **Nothing mitigates bleed.** PoE answers it with immunity flasks, % physical mitigation covering degeneration, ailment damage reduction, faster ailment damage and reduced duration — none of those five exist in this game. There is no status resistance either. The only answers are heal and Energy Shield, which shorten the race. Recorded as a deliberate gap rather than an oversight.
- **Trigger: the curse `Lacerate`** (Str scale, 14 sec cd, 10 sec duration, 40% chance per landed physical hit, 71% uptime) — PoE's `Vulnerability`, placed in the pool we already have for "make the target worse". Curses attach with the normal accuracy roll, so no new roll was invented. Curse roster 10 → 11, total roster 43 → 44.
- **Mob side deferred.** Mobs currently use their innate Element as their only skill; the owner will give selected mobs their own skill lists and then decide which mob type inflicts bleed.
- **Not yet folded into `mob_HP`** (checks.md D21). Deferred to the balance audit under the D-012 policy.

## D-014 — Mod availability is generated, not typed (applied)

`equipment-slot-pools.md` carries a `mod-matrix` block listing every Mod against every slot. It is written by `tools/check.js --write` from three sources: every Base row in `item-base.md` (Primary + Secondary union per slot), the main-hand table in `equipment-slot-weapon.md` (Role rows plus the By-weapon-type table), and the Offensive Pool table in `equipment-slot-pools.md`. Editing a Base row changes the matrix.

Check **X18** guards it three ways: every name in the matrix must be a real Mod line in `mod-pool.md` (or one of the three Gear Mods / the two Stat Mod lines); no Offensive line may answer `yes` on a Defensive slot; no Gear Mod may appear outside the five armour slots.

Building it exposed a contradiction, now fixed: `equipment-slot-weapon.md` listed `Str flat` / `Str %` as a main-hand Secondary, which contradicted the rule already written in `equipment-slot-pools.md` that closes direct per-stat Mods on weapons. **There are no per-stat Mods** — every stat on every item arrives through Stat Mod, and a weapon type only decides *which* stat its Stat Mod favours. Main-hand Secondary is now `Attack speed % · Accuracy %`.

## D-013 — Three Mod pools, and no duplicate Mod line (applied)

- **Every Mod belongs to one of three pools**: **Offensive** (weapon slots only) · **Defensive** (the other 10 slots) · **Stat Mod** (neither — rolls on every item, max 2 slots, 1 Flat + 1 %, both may be the same stat). The Stat Mod pool was called "Core stat flat/%"; "Core stat" still names the 7 stats themselves, so "Core stat Vit" remains correct while the Mod is now "Stat Mod".
- **One item can never roll the same Mod line twice.** The only pairing allowed is Stat Mod Flat + Stat Mod %, including on the same stat. A Flat line and its % sibling are separate lines and may both roll. Legacy mods count, so Add mod stone can never be offered a line the item already holds.
  Reason: without the rule a single item compounds one line and its power grows quadratically, so one drop can jump a whole tier. With it, Add mod stone always has an unused line available and every drop is a different set.
- **Add mod stone stays fully random.** No chosen-mod mode was added: a chosen Add would turn the stone from a paid gamble into a guaranteed stat, and the crafting duty in this project is "raise Item quality with luck you paid for", not "buy a specific line".

## D-011 — Attack speed floor and crit overflow (applied)

- **Attack speed Cap 300 → 500.** The Cap is the clock floor: 0.2 sec between hits = 5 times/sec. No weapon reaches it (`K_AGI_ASPD` left at 0.25, so the fastest weapon needs Agi 845 against the 816 ceiling), which makes it a safety rule for stacked buffs rather than a build target. The old intent "staff and two-handed are the only weapons cut by the Cap" is dead and was replaced in `check.js` X13.
- **Critical chance has no Cap; the 100 line became a spill point.**
  `crit_chance = min(crit_pool, 100)` · `crit_overflow = (crit_pool − crit_chance) × K_CRIT_OVERFLOW` with `K_CRIT_OVERFLOW` = 1.0 · overflow adds to crit damage (physical and magic both).
  Reason: a chance stat above 100 cannot make a hit crit twice, so the excess used to be discarded. Stats alone reach 48.8%, so overflow is 0 until buffs and skills push past 100 — the reward lands on crit-stacking builds instead of the Lck ceiling.
- **`Critical chance %` has no Flat anywhere.** `mod-pool.md` already ruled this; `engine.json` still carried `crit_chance_main_hand: 8` as a flat and `check.js` B6 added it flat. Renamed to `crit_pct_main_hand` and read as a percentage, which makes the doc and the data agree (X15 now reads the real mod-pool row).

## D-010 — Incoming defense layers follow PoE order (applied)

Ruling: the layer order in `combat.md` §2 is PoE's, not a local arrangement.

- **All mitigation runs before any pool is touched.** Order is roll to miss (`perfect_dodge` → `evasion` → `dodge`) → split → `armour` → Elemental res → Energy Shield → HP.
- Elemental res was previously listed *after* Energy Shield. That let ES absorb damage res should have removed, so the two were additive on one hit rather than multiplicative on survival time. Res moved ahead of ES.
- `armour` uses PoE's `armour / (armour + 5 × raw_physical)` on the physical half only.
- **Armour does not reduce DoT** (PoE rule), recorded in the file. Burn and poison counters stay res and perfect dodge.
- `perfect_dodge` stays at the top of the order. It has no PoE equivalent; it is defined as removing the hit that dodge cannot contest.

Consequence: the `731 armour = 10% mitigation` anchor in `skill-pool-aura-heal.md` was computed as `armour/(armour + 5 × 1316)`, which treats the boss's whole 1,316 as physical. With the 50/50 split the real mitigation is half that. Anchor must be restated (B-1).

## D-003 — Normalization infrastructure (applied)

**Problem** — a single roster change (aura 6 → 12) required hand-editing ~10 files, because
counts, names and cross-file references were typed as prose. The `patch/` file had to be
deleted after use, losing its rationale.

**Ruling** — extend the existing "data file → cage → generated block" pattern to the
roster and the tree wiring:

- `tools/data/skills.json` is the roster source of truth. Counts, names, reserves and
  effects are derived; no skill count is hand-typed.
- `tools/skills.js --write` regenerates the roster tables in `skill-pool*.md`; `--checks`
  runs the D18 mechanic gate.
- `tools/data/tree.json` owns branch/limb shape + the 18 keystones. `tools/tree.js` parses
  the 122 minor node tables, validates every `Enables` cell against the roster, and
  regenerates the summary in `skill-tree.md`. Known-pending refs are waived in
  `tree.json` `pending_refs`, so a *new* dangling ref fails but the tracked backlog does not.
- `tools/lint.js` is the referential guard: imports, markdown file references and line
  citations, deprecated terms, heading counts, marker balance.
- `tools/verify.js` runs every cage + the linter; `.githooks/pre-commit` calls it.

**Rule for future edits** — change the data file, run the writer, run `node tools/verify.js`.
A number or a name appears in exactly one non-generated place.

## D-007 — Skill workshop and rate columns (applied)

**Ruling** — one shared model (`tools/lib/skillmodel.js`) computes per-press damage, effective cooldown, presses/sec and mana/sec from the skill data + `meta.formula` constants. It powers three views:

- `node tools/skills.js --calc [--stat N --power N --level N --cdr N --ladder N]`
- the live "Skill workshop" section in `dashboard.html` (`node tools/report.js`)

**Not done (deliberate)** — the published `damage` columns stay hand-carried; deriving them from the model is a separate decision (it would move published numbers and force a D15/D17 rerun). D-004 still forbids restating a value in prose.

## D-006 — No reservation Cap; the player manages the set (applied)

**Problem** — the 45% Cap was a system limit that decided how many auras could run, which took the choice away from the player.

**Ruling** — drop the Cap. The player opens and closes auras directly. The only system rule is a block: total reserved mana may not reach 100% of the pool, so some mana always stays usable for skills. `skills.json` `meta.reservation.max_pct` records the 100% block. With all 12 auras summing to 110% (3×8 + 4×11 + 3×14), the full set can never run and the player must choose.

**Removed** — the automatic top-down opening, the "auras open at once = 3-5" note, and the cheapest/heaviest legal-combination lines (all Cap-based).

## D-005 — Tree wiring is rename-proof (applied)

**Problem** — node `Enables` cells referenced skills by display name, so renaming a skill left stale names in `skill-tree-*.md` that only a human could fix.

**Ruling** — a rename is recorded once in `skills.json` `renames` (`"Old Name": "New Name"`). `tools/tree.js --checks` reports the affected cells as PENDING; `--write` rewrites them automatically. The node prose stays in the md (readable); the link lives in data. Verified: renaming `Frost Nova` flagged 2 cells, `--write` updated them, no md hand-edit.

**Also** — L7 (value drift) now covers every doc except `harness/decisions.md`.

## D-004 — Prose must not restate a generated value (applied)

**Problem** — the JSON owned the roster, but prose still quoted the same values. Demonstrated: changing `Wraith of Fury` from `aspd +12%` to `+15%` in `skills.json` updated the generated table while the sizing bullet still read `+12%`, and `verify` passed — a silent drift.

**Ruling** — the generated table is the only place a skill/aura's own value appears. Text explains *why* and refers to the row. `tools/lint.js` L7 enforces it in `skill-pool*.md`: a line naming a skill/aura may not quote a signed percentage its data does not contain. The roster prose was swept clean (sizing bullets, blockers, the Cleave example).

**Still open** — the same pattern exists in `combat.md` / `checks.md` (derived combat numbers) and `harness/decisions.md` (historical values). Those sit outside L7's scope by design: the first two are owned by the pending `tools/survival.js` rerun, the last is a log.
